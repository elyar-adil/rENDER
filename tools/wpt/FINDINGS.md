# WPT runner: what the numbers mean

Findings from the Web Platform Tests conformance runner at
`tests/wpt_runner/`, run against WPT revision `c7fdee80f3f17b4e9813964916afdfd57ace863f`.

Fold this into `docs/wpt.md`. Everything below was measured, not estimated, unless
a line says otherwise.

## The headline

**No CSS/DOM/HTML conformance number is obtainable from this engine today, and
the blocker is structural, not a bug.**

The number most people would quote — "X% of WPT" — cannot be produced honestly,
and the reason is worth more than any percentage would have been. WPT's CSS
tests are, essentially without exception, `testcss.js` tests. `testcss.js` is an
**iframe driver**: `test_parsed_value`, `test_computed_value`,
`test_invalid_value` and the whole `test_*_rule` family each create a child
browsing context, write a stylesheet into it, and read values back out of it.

`render-core` does not implement nested browsing contexts. Its own spec registry
says so at `crates/render-core/src/spec/registry.rs:687`:

> Nested browsing contexts are not, so an `iframe` renders as nothing and
> `window.open` and `target=_blank` do nothing.

So the largest area with a real cascade, a real selector matcher and a real
layout engine is the one area whose test harness cannot run. That is a missing
capability, not an engine defect, and the two must not be confused: a missing
capability is a roadmap item, a defect is a bug.

**The defensible claim is a feasibility figure, not a conformance figure**, and
it is in `tools/wpt/results/wpt-results.json` with its denominator attached.

## What was run

One command. It self-checks, fetches if needed, runs, and writes results:

```powershell
powershell -File tools/wpt/run.ps1
```

Variants: `-Census` for the population/feasibility half only (no engine, and
the half that does not depend on the engine being healthy); `-Engine` to build
the `render-core` adapter; `-Areas css` to narrow scope; `-Limit N` for a
partial run, which is labelled `PARTIAL` and is never presented as a conformance
rate.

The first run needs network. It fetches the pinned revision from
`codeload.github.com` — 99 MB compressed, 167,893 archive members, 113 MB on disk
after extracting only the six trees under test. The full suite with history is on
the order of gigabytes.

The six trees are `css/`, `dom/`, `html/`, `resources/`, plus `common/` and
`fonts/`. The last two are **not test areas**: `common/` holds
`subset-tests-by-key.js`, `gc.js` and `get-host-info.sub.js`, and `fonts/ahem.css`
is the font every CSS metrics test uses. Omitting them made ~3,600 tests report
*missing fixture* — a true statement about the wrong thing, since the fixture
does exist at the pinned revision and the fetch simply had not taken it. A wrong
"missing fixture" is worse than an admitted scope limit, because it reads as a
suite defect.

## The population, and why the denominator is stated

WPT does not commit a test manifest — `MANIFEST.json` is generated by the `wpt`
tooling and is absent from the tree at the pinned revision, verified against the
GitHub tree API. So the population has to be derived, and a derived population is
a claim rather than a fact. The runner states it:

**46,325** `.html` files across the three test areas. After named exclusions the
scored population is **32,576**, and the arithmetic closes line by line in
`population_statement` in the results file. Per area:

| Area | files present | scored tests | excluded (by cause) |
| --- | --- | --- | --- |
| `css/` | 35,417 | **26,614** | 8,667 reference, 109 support, 6 manual, 17 tooling, 4 unreadable |
| `dom/` | 564 | **559** | 3 reference, 2 support |
| `html/` | 10,344 | **5,403** | 989 reference, 106 support, 346 manual, 28 tooling, 31 unreadable, 2,495 canvas, 960 browsers |
| **total** | **46,325** | **32,576** | |

The two scope exclusions are decisions, not accidents, and both sit *inside*
`html/` where they would otherwise silently inflate its denominator with tests
this engine cannot attempt:

- `html/canvas/` — 4,990 files. Canvas is explicitly out of scope.
- `html/browsers/` — 1,921 files. Browser-specific behaviour, not a conformance
  claim against a specification.

### Reference identity is structural, not conventional

WPT reftest references are named `*-ref.html` by convention. The runner
**checks that convention against the structural signal** — a file is a reference
if something else `link rel="match"`es it — and reports the agreement
(`reference_rule_agreement` in the results). This is a cheap way to catch a
denominator that is quietly wrong: if the two rules disagree by much, the
population arithmetic is suspect and says so.

Measured, at the pinned revision:

| Area | `rel=match` targets | named `*-ref.html` | in both | naming rule would miss | naming rule would drop |
| --- | --- | --- | --- | --- | --- |
| `css/` | 8,703 | 8,695 | 8,319 | 384 references | 376 real tests |
| `dom/` | 4 | 3 | 3 | 1 | 0 |
| `html/` | 998 | 767 | 720 | 278 references | 47 real tests |

The two rules agree on the bulk and diverge by hundreds, in **both** directions.
Had the runner used the naming convention alone it would have scored 384
reference files as tests and dropped 376 real tests — inflating the denominator
and the pass count together, which is invisible in the output.

Two resolution rules matter here and both were found by the disagreement, not by
inspection:

- WPT serves **two bases**: a rooted URL (`/css/reference/square.html`) is
  suite-root-relative, and a relative URL (`../shared/x.html`) is relative to the
  referring file. Treating a rooted URL as unresolvable misclassified 378 real
  references as tests.
- `link rel="match" href="about:blank"` is a **legitimate WPT idiom** — "this
  must render as a blank page" — and is not a missing file. Reporting it as an
  unresolvable reference produced 3,654 css notes and buried the genuine cases in
  noise, which is the same failure as missing them entirely.

## Four states, because three are not enough

The core design constraint, and the one most likely to be violated by a future
change. Every result is exactly one of:

| State | Meaning |
| --- | --- |
| `pass` | every assertion was evaluated and held |
| `fail` | an assertion was evaluated and did not hold; **the failing assertion is recorded** |
| `error` | the harness could not evaluate the test. Never a pass, never a fail |
| `skip` | not run, with a reason from a fixed vocabulary |

A runner that reports a thrown adapter as a failure manufactures failures; one
that reports it as a pass manufactures passes. The second is the dangerous one,
because it survives review. A conformance number produced by a harness with that
bug would be quotable, believable, and wrong.

The state arithmetic refuses the conflation directly: `Tally::engine_rate()`
computes over `pass + fail` only, returns `None` when nothing was attempted, and
returns a `Rate` that cannot be displayed bare. **There is no code path in this
crate that prints a percentage without its denominator**, and
`results::tests::rate_string_always_carries_its_denominator` is the test that
keeps it that way.

## The harness is checked before it is trusted

`wpt-runner selftest` runs **before any scoring**, on every subcommand, and its
result is embedded in the results file. Nine checks, each aimed at a specific way
the number could be quietly wrong:

```
9 of 9 checks held
harness trustworthy: yes
```

The checks cover: a failing assertion reports `fail` with the assertion text; a
satisfied one reports `pass` **and records how many assertions were evaluated**;
an adapter error is `error` and not `fail`; **a panicking adapter is contained
and becomes `error`**; an unsupported capability is `skip` and not `fail`; a
test with no assertion is flagged cannot-fail and not executable; a rate always
renders with its denominator; a test needing a missing capability is blocked and
never executable; and an unavailable engine yields **no rate at all**, not a
zero rate.

That last one is the check worth keeping. "0% conformance" produced by a runner
that could not start is a false claim about the engine, and it is exactly the
kind of number that gets quoted. `Rate` returns `None` when the denominator is
zero, and `outcome::tests::empty_tally_has_no_rate_rather_than_a_zero_percent`
enforces it.

The panic containment matters more than it looks. A WPT document is hostile
input; somewhere in a layout solver it will index out of bounds or recurse out of
stack. An escaping panic kills the process and leaves a **truncated result file
that looks like a smaller suite** — the worst possible failure mode, because it
is invisible. `engine::run_one` wraps every adapter call in `catch_unwind` and
maps a panic to `error`.

## Tests that could not fail

Counted and reported, never scored. This is the same failure mode that inflated a
test count in this project and was only found by accident, so it is a
first-class metric rather than a footnote.

**Measured: 6,466 of the 32,576 scored tests declare no assertion site at all
(19.8%).** By area: 4,782 in `css/`, 132 in `dom/`, 1,552 in `html/`. Most are
reftests whose comparison is a `link rel=match` the scanner could not attribute,
plus crash-guard tests that assert only that the page did not crash. A crash
guard is a real WPT idiom, not a defect — but scoring it as a *pass* inflates the
pass count, which is exactly what this metric exists to make visible.

- **Statically, at census time:** a test whose source contains no assertion call
  site and declares no reftest reference. It has no way to fail in any browser.
- **At run time:** a test the adapter reports as `pass` having evaluated **zero**
  assertions. `Report::vacuous_passes()` counts these. The two are different
  measurements — the static one is a property of the test, the runtime one is a
  property of the run — and both appear in the results file. The run-time count
  is **0** in this run, because nothing was executed.

The classifier excludes method calls (`obj.assert_true(...)` is not an assertion)
and function declarations (`function test() {}` is not a call site), because
counting either inflates the "has assertions" signal and hides a vacuous test.
Both exclusions were added after the self-check caught the classifier scoring
`obj.assert_true(...)` as an assertion site.

## Engine defects

**None reported, and that is a finding rather than an absence of one.**

No engine defect can be reported from a run in which the harness could not
evaluate the tests — not because the engine is clean, but because nothing was
tested. The binding constraint is `nested-browsing-context`, which gates the CSS
area wholesale, and the CSS area is where a real defect list would have come
from: the engine has a real cascade, a real selector matcher and a real layout
engine, so WPT's CSS corpus is exactly the instrument it needs.

**The defect list is blocked, not empty.** Any engine defects reported from this
run would be an artefact of the harness, which is the specific failure this
runner was built to prevent.

### Two defects found in the *instrument*, not the engine

Reported because they are the same class of problem this project keeps hitting,
and because a runner with these would have produced a wrong number while looking
entirely healthy.

**1. The reference-identity metric was silently broken** (fixed). The runner
stores `rel=match` targets and `*-ref.html` names in two sets and reports their
intersection. The first version stored the URL as written (`b-ref.html`) in one
set and the suite-relative path (`css/a/b-ref.html`) in the other, so the sets
were **disjoint by construction**. The report said "0 in both; the naming rule
would have missed 8,748 references and dropped 8,695 real tests" — a number
impossible on its face, produced without a single error.

The lesson is the point: nothing failed, no test caught it, and the output was
plausible. It was caught only by *reading the number and noticing it was absurd*,
which is the only defence there is against a metric that is wrong in a
consistent direction. `normalize_against` now puts both sets in one key space,
and `census::tests::reference_urls_normalize_into_the_same_key_space_as_paths`
pins the behaviour.

**2. A fetch bug doubled the entire population** (fixed). Re-fetching onto an
existing cache made `Copy-Item -Recurse` copy *into* the existing directory
rather than replacing it, producing `css/css/`, `html/html/`. Every count roughly
doubled — 92,650 files instead of 46,325, 65,162 tests instead of 32,576 — and
the tree still looked like a plausible WPT checkout. Nothing errored.

Two defences are now in place, and the second is the one that matters: the fetch
replaces trees rather than merging, and the **census refuses to run** against a
self-nested checkout (`assert_cache_not_nested`) with a message naming the
cause. A measurement tool that cannot detect a corrupted input is not a
measurement tool.

## Contracts needed from the engine

Reported, not worked around. The runner works without all three.

### 1. Distinguish "does not apply" from "not implemented" on a computed value

`render_css::computed::ComputedStyle::get` (`crates/render-css/src/computed.rs:301`)
takes a property name and returns `Option<&ComputedValue>`. `None` is ambiguous
between *the property does not apply to this element* and *the engine does not
implement the property*. Those need different verdicts — one is a pass, the other
is a skip. Needed:

```rust
pub enum ComputedValueLookup {
    /// The property applies and the engine computed it.
    Value(ComputedValue),
    /// The property applies to this element but is not initialised.
    NotInitialised,
    /// The engine does not implement this property at all.
    Unsupported,
    /// The property does not apply to this element.
    DoesNotApply,
}

impl ComputedStyle {
    pub fn lookup(&self, property: &str) -> ComputedValueLookup;
}
```

Without this, an adapter that reads a fixed property list gets a vacuous pass for
every property the engine does not implement — which is precisely the inflation
this section exists to prevent.

### 2. Source location of the declaration that won the cascade

To report a CSS failure as an engine `file:line`, the winning declaration's
origin has to survive the cascade. **The parser has it and the cascade throws it
away.** `StyleSheetDiagnostic` carries `line` and `column`
(`crates/render-css/src/stylesheet.rs:52`), but `Declaration` (`stylesheet.rs:35`)
has only `name`, `value` and `important`, so by the time a computed value exists
the origin is unrecoverable. Nothing in the current API can get it back. Needed:

```rust
pub struct Declaration {
    pub name: String,
    pub value: String,
    pub important: bool,
    /// 1-based line in the originating stylesheet. 1-based because
    /// `StyleSheetDiagnostic` already is; the two must not disagree.
    pub line: u32,
    pub column: u32,
}

// and, on the computed side, alongside the value:
pub struct ComputedValue {
    pub value: String,
    /// The declaration that won the cascade for this property, if any.
    pub origin: Option<DeclarationOrigin>,
}

pub enum DeclarationOrigin {
    Author { line: u32, column: u32 },
    UserAgent { line: u32, column: u32 },
    Inline,
}
```

The `line`/`column` fields on `Declaration` are almost free: the parser already
computes them a few lines away at `stylesheet.rs:1270`, and they are discarded in
the conversion. This is the single highest-leverage contract in this document,
because it is what turns "a WPT test failed" into "this function is wrong".

### 3. Load an external stylesheet from a `file://` URL

`DocumentRenderOptions` and `ExternalStyleSheetKey` support injecting a sheet
*by key*, and `discover_author_style_slots` enumerates the slots — but there is no
loader, and nothing resolves a WPT-relative URL against the suite layout. The
adapter would have to reimplement the resolution, which is a bug farm, and a bug
there produces a confidently wrong CSS result. Needed:

```rust
pub trait ResourceLoader {
    /// Resolve `href` against `base` and return the bytes, or `None` when the
    /// resource is genuinely absent. `None` must not be conflated with a fetch
    /// error, or a missing fixture reads as an empty stylesheet.
    fn load(&self, base: &Url, href: &str) -> Option<Result<Vec<u8>, String>>;
}
```

## Harness limitations, stated as such

Not engine defects, and not counted as such:

- **Legacy `setup()` harness.** Detected and reported as
  `unsupported-harness-shape`. A gap in this runner.
- **The `testcss.js` entry points are not reimplemented.** The adapter declines
  them. Reimplementing `test_parsed_value` as "apply the declaration, read the
  value, compare" would drop the iframe, and the iframe *is* the test: it is how
  the suite checks that a fresh document with a fresh stylesheet computes a value
  the way a browser does, including the initial-value and origin questions a
  hand-rolled harness gets right by accident. A harness that reimplements the
  entry points would report a CSS pass rate that measures the harness.
- **The adapter reads a fixed property list** (`KNOWN_PROPERTIES` in
  `render_core.rs`), because the engine does not expose its property table.
  Reading every property would need contract 1 above.
- **Capability detection is lexical.** A capability reached through indirection
  is missed. The classifier errs toward *blocking* in this case, which costs an
  explained skip rather than a false claim of runnability.

## A contradiction with docs/wpt.md

`docs/wpt.md` says the runner there is "the Rust integration test
`crates/render-core/tests/wpt_reftests.rs`" and that the WPT checkout is fetched
by `tools/fetch-wpt.ps1`, pinned, verified, into an external directory. Both
statements were checked and both are now stale:

- **`tools/fetch-wpt.ps1` does not work on this host.** It uses `git fetch` and
  `git checkout` against `github.com`, and the global git config forces a SOCKS5
  proxy at `localhost:10808` that is not running, so every git operation against
  GitHub fails. `tools/wpt/fetch-wpt.ps1` uses the codeload tarball over plain
  HTTPS instead and works.
- The reftest path is out of scope here and is not replaced. This runner measures
  *assertion* conformance via the testharness and `testcss.js` entry points; the
  existing reftest runner measures rendered-reference comparison. They answer
  different questions and both are worth having.

`docs/wpt.md` should link to this file rather than duplicate the numbers, which
would go stale on the next run.

## Operational note: the suite is fetchable

`docs/wpt.md` records that the suite may be unavailable. **It is available, and
the fetch works.** Two environment-specific notes for whoever runs this next:

- The global git config on this machine sets
  `http.https://github.com.proxy=socks5://localhost:10808`, and that proxy is
  **not running**. `git ls-remote` against `github.com` fails with
  `Failed to connect to localhost port 10808`. Ordinary HTTPS works fine, so the

## What was not done, and why

- **No CSS conformance rate.** Blocked on nested browsing contexts. Not a defect
  in the engine; a capability it does not have.
- **No engine `file:line` in any failure record.** Blocked on contract 2. Without
  it a failure can say what broke but not where in the engine, which is why the
  `engine_location` field in the results is currently always empty rather than
  guessed.
- **No pixel comparison.** The reftest path needs a rasteriser and a reference
  decode; the existing `crates/render-core/tests/wpt_reftests.rs` covers the
  static reftest route and this runner does not duplicate it.
- **No manual or tooling tests**, and no `canvas/`, `webgpu/`, `webaudio/`,
  `webrtc/`, `wasm/`, `network/`, `service-workers/`, `storage/`. Excluded by
  decision, and each exclusion is its own bucket in the results.
- **The `--features engine` adapter is written but never compiled or executed.**
  `render-js` did not build at any point during this session, and the engine
  crates were under active concurrent edit. Verified failure, reported rather
  than worked around:

  ```text
  error[E0004]: non-exhaustive patterns: `&ObjectHost::DomExceptionConstructor` and
                `&ObjectHost::DomException { .. }` not covered
  error: could not compile `render-js` (lib)
  ```

  `cargo build -p render-core --lib` fails the same way, so this is the engine's
  state and not the adapter's. The adapter is **unproven code**: it has never been
  compiled, so treat it as a sketch until someone runs it. Everything else in this
  report — census, population, feasibility, self-check — is fully exercised, and
  none of it depends on the engine compiling. That separation is why the engine
  dependency is an optional feature: the trustworthy half of the work keeps
  working while the engine is broken.
- **Not attempted: running `test262`**, per the task constraints.
